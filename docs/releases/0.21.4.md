TabStudio 0.21.4 makes containers hold up in real projects on a real tablet: when Android ends the app halfway
through creating one, when memory runs low, when a second window opens, and when a Compose file uses the settings
people actually write. Each fix has a test that failed before it.

## Fixed

- **One engine per store.** Two container engines on the same store, such as a second TabStudio window, overwrote
  each other's image index and container records. The first engine now owns the store until it closes. A second one
  can still show the containers, but it can't change them, and it says why. The lock is released when the app's
  process ends, so a TabStudio that Android ended never blocks the next one.
- **No half-copied containers.** When Android ended TabStudio while it was copying a container's files, the partial
  copy stayed in storage, and so did unpacking work and half-written records. They are removed in the background
  the next time TabStudio starts. Downloads are kept, because they resume.
- **Low memory stops a container, not the IDE.** Android ends an app together with every process it started, so a
  database's memory could cost the whole IDE. When Android says memory is low, TabStudio now stops the running
  container that uses the most memory. The Containers window says which one it stopped and why. A container's
  processes are also the kernel's first choice when memory runs out. A container killed by the system says so,
  instead of showing only "exited 137".
- **Restart policies restart.** `restart: always`, `unless-stopped` and `on-failure` never restarted anything: the
  monitor checked a cancellation it had just made itself. They now work as they do in Docker. Containers set to
  `always` or `unless-stopped` that were not started from a Compose file also start again when TabStudio starts.
- **Compose `container_name`, `hostname`, network `aliases` and `expose`.** The container takes its
  `container_name`, and other services reach it by that name, its aliases and its hostname. Exposed ports are
  mapped like the image's own.
- **Image `VOLUME` data survives a changed setting.** A Compose service whose data lives in a volume that only the
  image declares, such as Redis's `/data`, lost that data whenever a changed setting created its container again.
  That volume now belongs to the service, as in Docker Compose. Data from 0.21.1 moves over the first time.
- **`build:` with `image:`.** A service that builds its image and names it is still pulled first, as Compose does.
  When the image is in no registry, the message names the Dockerfile it would be built from, instead of showing a
  registry error.
- **Readiness follows the image.** Services waited 120 seconds for every image, then quietly started a native
  service in its place, with different data. Now the wait lasts as long as the image's health check allows, and an
  image that keeps writing its log while it initializes gets up to ten minutes. The row shows what it is waiting for.
  An image that started and then failed, or never became ready, fails with its own reason and its logs. Only an
  image that can't run here at all falls back to a native service. When that happens, the F5 Output says so in a
  warning, along with the reason.
- **Readiness waits on the ports that matter.** Services waited for every port an image declares, but images
  declare ports they never open, such as MariaDB's 33060 and RabbitMQ's 5671. The ports a Compose file publishes
  must answer now. When it publishes none, one of the image's own ports answering is enough.
- **`80:80` works.** A port below 1024 needs root, which apps don't have. Most web stacks publish `80:80`, and those
  services failed with "port 80 is already in use". An image's privileged port now gets a free unprivileged one, and
  the row shows which.
- **Removing a container while it stops.** When a container was removed just as its exit was being saved, the stop
  failed with a missing-file error.
- **Clear reasons for images that can't run here.** An image whose command starts systemd, or whose program is
  built for a different processor than the image says, gets a one-line reason before it starts, instead of a bare
  exit code.
- **Cleanup.** Pruning also removes the volumes that only a removed container could ever have used.

## CI

- The Android emulator (containers) shard failed once on `main` for 0.21.1 because the runner had 7.4 GB free when
  the emulator needed 9.6 GB for its data partition. The emulator stopped at once, and the runner action then waited
  out its whole 600-second boot timeout. Every emulator shard now removes build output and unused preinstalled tools
  first, then fails at once with the free space if there still isn't enough.
- Publishing logs to `ci-logs` checked out that branch's whole tree, gigabytes of every job's logs and screenshots.
  On a full runner this failed a job whose tests had already finished ("Disk quota exceeded"). Only the job's own
  folder is written to disk now.
- The compatibility job starts five more images (WordPress, Gitea, Grafana, Prometheus and Traefik) and two public
  Compose stacks from their own files, pinned to a commit: docker/awesome-compose's `wordpress-mysql` and
  `gitea-postgres`. All five images work on x64 and ARM64. Both stacks start and answer on both architectures
  (WordPress in 22 to 26 seconds, Gitea in 6). `wordpress-mysql` did not start before the readiness and port fixes
  above.

## Install

1. Download `TabStudio-0.21.4.apk` below on your tablet.
2. Open it and allow installing apps from your browser or file manager when Android asks.

Requires Android 9 or later on 64-bit or 32-bit ARM, with 3 GB of memory or more (2 GB with TabStudio Link). It installs
as an update over 0.21.

## Verified

Every commit runs the unit tests of every library, headless UI tests of the real IDE in both themes, an APK build with
signature verification, and the self test on an Android tablet emulator in five shards. New tests cover each fix:
two engines on one store, recovery from a cut-short create, the cleanup of orphaned volumes, which containers start
again, the systemd and processor checks, the Compose names, readiness, and fallback only for images that can't run.
With real images under PRoot on x64 and ARM64, they also cover `on-failure` restarts, a low-memory stop, a system
kill followed by a restart, and a Compose service's image volume surviving a new container.
